## 25.1 Chapter Introduction

In **Chapter 24**, we built the first layer of an executable ontology: the **boundary layer**. Universal restrictions told the reasoner what wa allowed; closure axioms closed the world around those boundaries. By the end of that chapter, the ontology could classify `MargheritaPizza` and `SohoPizza` as `VegetarianPizza` -- deterministically and without ambiguity.

But a boundary tells the system what is *permitted*, it does not tell the system what to *do*.

Consider a pizza that is `Hot`. Or an order whose status is `Pending`. Or a customer whose tier is `Gold`. Each of these is a specific value -- not a boundary, not a range, but one point in a closed set. Execution often fires on exactly these points. "If the spiciness is `Hot`, alert the kitchen. If the order is `Pending`, send a reminder. If the tier is `Gold`, apply the discount."

Chapter 25 builds the layer that makes these triggers possible: the **value layer**.

The value layer has two halves:

- An **enumerated class** closes the *value domain* -- it declares the complete, finite set of values a property may take. `Spiciness = {Hot, Medium, Mild}`. No other value is possible.
- A **`hasValue` restriction** binds a property to *one specific value* from that domain. `JalapenoPepperTopping hasSpiciness value Hot`. Not a class of values -- the value itself.

Together they allow the ontology to express and execute rules that depend on *specific values* rather than *categories*. This is the semantic foundation of the trigger.

This chapter follows **Exercise 24** and **Exercise 25** in Michael DeBellis' *Protégé 5 New OWL Pizza Tutorial*, read through the lens of executability. It is the second of three chapters on **Stage 7 -- Executable Knowledge** .

**Key Insight:**

> "A boundary tells the system what is allowed. A value tells the system what to act on. The value layer is where execution becomes specific."

### 25.1.1 How Chapter 25 Continues Chapter 24

Chapter 24 built the boundary layer from two primitives: the universal restriction (**Exercise 22**) and the closure axiom (**Exercise 23**). Chapter 25 builds the value layer from two more: the enumerated class (**Exercise 24**) and the `hasValue` restriction (**Exercise 25**).

| Layer | Primitive | Exercise | What It Closes |
| --- | --- | --- | --- |
| Boundary | Universal Restriction (`only`) | Ex 22 | What is permitted |
| Boundary | Closure Axiom | Ex 23 | What exhaustively exists |
| Value | Enumerated Class | Ex 24 | The set of possible values |
| Value | `hasValue` Restriction | Ex 25 | The specific value to act on |
| Integrity | Cardinality Restriction | Ex 26 (Ch 26) | The number of values required |

Each layer depends on the one before it. The value layer is meaningless without the boundary layer -- binding a value to a property whose permitted range is not closed would leave the binding ambiguous. Conversely, the boundary layer is incomplete without the value layer -- a boundary that cannot fire on specific values cannot drive action.

**Key Insight:**

> "The boundary layer says what is closed. The value layer says what to fire on. Execution needs both."

## 25.3 A Brief Note on OWL Design Patterns

Before we build our next execution primitive, it is worth pausing to name a concept that has quietly been present throughout this book: **the design pattern**.

The idea of a design pattern comes originally from architecture -- Christopher Alexander's *A Pattern Language* (1977) -- and was brought into software engineering by the "Gang of Four" in their 1994 book *Design Patterns*.

> **Alexander's insight** was that good design does not begin from nothing; it draws on a shared vocabulary of proven solutions to recurring problems. Each solution can be adapted to a specific context without being reinvented.

In OWL, the same idea applies. A **design pattern** is a reusable combination of OWL constructs that solves a recurring modeling problem. It sits at a higher level of abstraction than a single class or axiom -- it is a **shape**, not a thing!

By this point in the book, you have already used several OWL design patterns without necessarily calling them that:

| Pattern | Introduced | Purpose |
| --- | --- | --- |
| **Probe Class** | Chapter 22 (Exercise 19) | A deliberately inconsistent class used to test whether validation infrastructure works |
| **Closure Axiom** | Chapter 24 (Exercise 23) | A universal restriction that closes the world for a class or individual |
| **Enumerated Class** | This chapter (Exercise 24) | A class whose extension is defined by listing all of its instances |
| **`hasValue` Restriction** | This chapter (Exercise 25) | A restriction that binds a property to a specific individual |
| **Cardinality Restriction** | Chapter 26 (Exercise 26, upcoming) | A restriction on the number of values a property may have |

Each of these is a **reusable shape**, not a one-off modeling decision. You can apply the same shape to any class in any domain -- pizza, manufacturing, financing, healthcare -- and it will work the same way.

That reusability is what makes design patterns valuable for governance and execution:

- **Reuse**: A pattern written once can be instantiated many times.
- **Consistency**: Different engineers applying the same pattern produce structurally similar (or even same) models.
- **Governance**: Patterns can be named, documented, and governed like any other asset.
- **Execution**: The execution primitives in this chapter (closure, enumeration, `hasValue`, cardinality) are effectively the design patterns of Stage 7.

The full OWL design pattern landscape -- the ODP catalog (http://www.ontologydesignpatterns.org/index.php/Ontology_Design_Patterns_._org_(ODP)), logical vs. content patterns, pattern composition, and pattern selection strategies -- is a topic of its own. It belongs to the era of **Knowledge Graph Engineering**, when you are building systems that span multiple ontologies and reuse libraries of proven patterns.

We will return to it in **Volume 5**.

For now, the key point is this:

> **when you build an execution primitive in this chapter, you are not just writing an axiom -- you are instantiating a design pattern.**

The patterns will grow with you as your ontology grows.

## 25.4 Exercise 24 -- Enumerated Classes and Deterministic Value Sets

Having established closure axioms in **Exercise 23**, we now turn to the first execution primitive of the **value layer**: the enumerated class.

As we saw in **Section 24.6.7**, the enumerated class is one of the design patterns of Stage 7 — here we instantiate it.

### 25.4.1 The Engineering Objective

**Exercise 24** introduces the **enumerated class** -- a class whose extension is defined by explicitly listing all of its instances.

An enumerated class for spiciness, for example, would be:

```text
Class: Spiciness
  EquivalentTo: {Hot, Medium, Mild}
```

This means: "The class `Spiciness` has exactly three instances: `Hot`, `Medium`, and `Mild`."

The engineering objective for **Exercise 24** is to demonstrate how enumeration provides a **complete, deterministic value domain** -- a prerequisite for execution.

Why does execution need enumeration?

Consider an execution rule that fires when a pizza is "spicy". For the rule to be reliable, the system must know the complete set of possible spiciness values. If the ontology only says "there exists a `Spiciness` value" but does not enumerate what that value could be, the rule cannot be exhaustively evaluated.

Enumeration closes the value domain. It says: *these are all the possible values -- nothing more, nothing less.*

This is the value-domain analogue of the closure axiom. The closure axiom closed the set of permitted *toppings* for a class; the enumerated class closes the set of permitted *values* for a property. Both replace an open-world description with a closed-world specification -- one at the property-range level, one at the value level. Together, they are the two halves of boundary closure.

**Key Insight:**

> "An enumerated class is a closed-world specification of a value domain. It says not just what values exist, but that **no other values exist.**"

### 25.4.3 The Result: A Deterministic Value Domain

The enumerated class has provided a **deterministic value domain** for `Spiciness`.

For execution, this is essential. When an execution system encounters a `Spiciness` value, it knows the value must be one of `Hot`, `Medium`, or `Mild`. It can handle all possible cases exhaustively.

Contrast this with the alternative. If we had only declared `Spiciness` as a class (with `Hot`, `Medium`, and `Mild` as asserted instances), the reasoner would still recognize those three individuals as instances of `Spiciness`. But it would not know that they are the *only* instances. Under the Open World Assumption, there might be other spiciness values not yet asserted.

Enumeration removes this uncertainty. The `EquivalentTo {Hot, Medium, Mild}` axiom does two things simultaneously:

- It says that `Hot`, `Medium`, and `Mild` **are** instances of `Spiciness` (sufficient condition).
- It also says that anything else is **not** an instance of `Spiciness` (necessary condition).

This is what makes enumeration a closed-world specification.

**Key Insight:**

> "Enumerated classes are the OWL equivalent of an `enum` in a programming language. They define the complete set of possible values -- nothing more, nothing less."

### 25.4.4 Why Enumerated Classes Matter for Execution

Enumerated classes are essential for execution because:

1. **The define finite value domains.** Execution systems need to know the complete range of possible values to handle every case.
2. **They enable exhaustiveness checking.** If an execution system handles `Hot`, `Medium`, and `Mild`, it has handled all cases -- because the ontology guarantees there are no others.
3. **They convert open-world value domains into closed-world specifications.** Without enumeration, a property might have unknown or additional values. With enumeration, all values are known.
4. **They compose with other execution primitives.** Enumeration works with `hasValue` restrictions (**Exercise 25**) and cardinality restrictions (**Exercise 26**) to build richer execution logic. For example, an execution rule can fire on `hasSpiciness value Hot`, confident that `Hot` is a fixed, well-known value from a closed enumeration.

The table below contrasts the behavior of a property with and without an enumerated value domain:

| Aspect | Without Enumeration | With Enumeration |
| --- | --- | --- |
| **Value domain** | Open -- any value is possible in principle | Closed -- only the listed values are possible |
| **Reasoner behavior** | Cannot exhaustively check value conditions | Can exhaustively check value conditions |
| **Semantic strength** | Description of a class | Specification of a value domain |
| **Execution readiness** | Not executable for value-based triggers | Executable for value-based triggers |

**Key Insight:**

> "Execution cannot handle unknown values. Enumeration is how the ontology guarantees that all values are known."

## 25.5 Exercise 25 -- `hasValue` Restrictions and Specific-Value Binding

Having established the enumerated value domain in **Exercise 24**, we now turn to **Exercise 25**, which introduces the `hasValue` **restriction** -- the construct that binds a property to a specific individual.

This exercise completes the value-binding layer of Stage 7. in **Exercise 24**, we closed the world for a *value domain* (`Spiciness = {Hot, Medium, Mild}`). In **Exercise 25**, we close the world for a *specific value* -- binding a property to one particular individual from that domain.

### 25.5.1 The Engineering Objective

**Exercise 25** introduces the `hasValue` **restriction**, which specifies that a property must have exactly one specific value.

A `hasValue` restriction for a spicy pizza, for example, would be:

```text
Class: SpicyPizza
  EquivalentTo: Pizza and (hasTopping some (hasSpiciness value Hot))
```

This means:

> "A pizza is a `SpicyPizza` if and only if (`iff`) it has at least one topping whose spiciness is `Hot`."

The engineering objective of **Exercise 25** is to demonstrate how `hasValue` restrictions enable **value-based execution logic** -- the ability to fire a trigger on a specific value rather than a general class of values.

Why does execution need `hasValue`?

Consider an execution rule that fires when a pizza's spiciness is `Hot`. For the rule to be reliable, the system must be able to detect the *specific value* `Hot` -- not just any value from the `Spiciness` class. The `hasValue` restriction is the OWL construct that expresses this specific-value condition.

Where **Exercise 24** gave us the *closed value domain*, **Exercise 25** gives us the *specific value binding*.

Together, they form the value layer of executability.

**Key Insight:**

> "The `hasValue` restriction is the semantic equivalent of a conditional statement. It says: if the value is $X$, then the condition is true."

> This is a different kind of restriction from the ones we have ever used before. This is why the keyword is `value` rather than `some` or `only`.

1. Make sure `Pizza` is selected in the class hierarchy
   ![ch24_67_ex25-select-pizza-class](img/ch24_67_ex25-select-pizza-class.png)
2. Click the **Add subclass** icon.
   ![ch24_68_ex25-add-subclass](img/ch24_68_ex25-add-subclass.png)

4. Click `OK`
   ![ch24_70_ex25-spicypizza-added](img/ch24_70_ex25-spicypizza-added.png)

**Step 7: Add the nested `hasValue` restriction to `SpicyPizza`**

1. Select `SpicyPizza`
2. In the **Description** view, locate the **SubClass Of** section
   ![ch24_71_ex25-spicypizza-subclassof](img/ch24_71_ex25-spicypizza-subclassof.png)
3. Click the Add icon (+)
   ![ch24_72_ex25-spicypizza-subclassof-add](img/ch24_72_ex25-spicypizza-subclassof-add.png)
4. In the Class Expression Editor, enter: `hasTopping some (hasSpiciness value Hot)`
   ![ch24_73_ex25-spicypizza-subclassof-exp](img/ch24_73_ex25-spicypizza-subclassof-exp.png)
5. Click `OK`
   ![ch24_74_ex25-spicypizza-subclassof-added](img/ch24_74_ex25-spicypizza-subclassof-added.png)

After this step, `SpicyPizza` has:

```text
Class: SpicyPizza
   SubClassOf: Pizza
   SubClassOf: hasTopping some (hasSpiciness value Hot)
```

This says: "A `SpicyPizza` must have at least one topping whose `hasSpiciness` property value is `Hot`." Note the *nesting*: `hasTopping some (...)` is an existential restriction whose filler is itself a `hasValue` restriction. This composition is what makes the pattern powerful -- a restriction inside a restriction.

**Step 8: Convert `SpicyPizza` to a defined class**

1. Make sure `SpicyPizza` is still selected
2. Select `Edit > Convert to defined class` (or from right-click menu)

Once the chain is complete, the reasoner can make the inference."

### 25.5.3 The Result: Value-Based Execution Logic

The `hasValue` restriction has enabled **value-based execution logic**.

For execution, this is essential. Many execution rules depend on **specific values**, not general classes of values.

For example:
- "If the temperature reading is `Critical`, then trigger an alert."
- "If the order status is `Pending`, then send a reminder."
- "If the customer tier is `Gold`, then apply a discount."

Each of these rules fires on a *specific value* from a closed value domain. The `hasValue` restrictions is the OWL construct that expresses this condition.

Contrast this with the alternative. In **Exercise 22**, we used to universal restriction (`hasTopping only ...`) to describe *what is allowed*. That restriction expressed a boundary, not a specific trigger. In **Exercise 23**, we used closure axioms to *close the world* for those boundaries. Now, in **Exercise 25**, we use `hasValue` to *bind a trigger* to a specific value.

The four constructs work together:

| Construct | Role | Exercise |
| --- | --- | --- |
| Universal restriction (`only`) | Defines what is allowed | Ex 22 |
| Closure axiom | Closes the world for a class or individual | Ex 23 |
| Enumerated class | Defines a closed value domain | Ex 24 |
| **`hasValue` restriction** | **Binds a property to a specific value** | **Ex 25** |

Each construct builds on the previous one. The universal restriction establishes a boundary. The closure axiom makes the boundary usable for classification. The enumerated class narrows the value domain to a finite set. And the `hasValue` restriction binds a trigger to one specific value within that domain.

**Key Insight:**

> "`hasValue` is the most direct connection between ontology and execution logic. It is the semantic equivalent of a state-machine transition -- `when the value is $X$, do $Y$.'"

### 25.5.4 Why `hasValue` Restrictions Matter for Execution

`hasValue` restrictions are essential for execution because:

1. **They bind properties to specific values.** Execution rules often depend on specific values, not general categories. The `hasValue` restriction is how OWL expresses this specificity.
2. **They enable precise triggers.** A trigger can be defined as "fire if the property has this specific value." Without `hasValue`, a trigger on `Spiciness` could fire on any spiciness -- `Hot`, `Medium`, or `Mild`. With `hasValue value Hot`, the trigger fires only on `Hot`.
3. **They compose with other constructs.** `hasValue` can be nested inside existential or universal restrictions, enabling complex conditions. The `SpicyPizza` definition -- `hasTopping some (hasSpiciness value Hot)` -- is a restriction inside a restriction. This composition is what makes the pattern expressive enough for real execution logic.
4. **They connect closed value domains to specific triggers.** In **Exercise 24**, we closed the value domain ("world") for `Spiciness`. In **Exercise 25**, we use that closed domain to bind specific triggers. The two constructs work as a team.

The table below contrasts the behavior of a property with and without `hasValue`:

| Aspect | Without `hasValue` | With `hasValue` |
| --- | --- | --- |
| **Trigger condition** | Fires on any value of the property | Fires on one specific value |
| **Reasoner behavior** | Cannot distinguish between values | Can distinguish specific values |
| **Semantic strength** | Description of a class of conditions | Specification of a specific condition |
| **Execution readiness** | Not executable for value-specific triggers | Executable for value-specific triggers |

**Key Insight:**

> "Every semantic trigger is ultimately a `hasValue` restriction somewhere. The trigger fires when the property has the specific value that the trigger was designed to detect."
